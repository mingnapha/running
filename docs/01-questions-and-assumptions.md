## B. คะแนนและอันดับ

| B1 | ⚠️ สูตรคะแนน ตัวอย่าง "3.0 กม. +30" แปลว่า 10 แต้ม/กม. | `points = round(distance_km × points_per_km, 2)` โดย `points_per_km` ตั้งต่อฤดูกาล (ค่าเริ่ม 10) |

| # | ประเด็น | สมมติฐาน |
|---|---|---|
| F1 | ข้อมูลที่เก็บ | รหัสพนักงาน, ชื่อที่แสดง (ชื่อเล่นหรือชื่อจริงตามที่พนักงานเลือก), แผนก, ข้อมูลการวิ่ง, รูปหลักฐาน — **ไม่เก็บ** อีเมลจริง เบอร์โทร วันเกิด GPS |

| F3 | ⚠️ 90 วันนับจากเมื่อไหร่? | นับจาก **วันที่อัปโหลด** ลบไฟล์ใน Storage ด้วย cron (Supabase `pg_cron` + Edge Function หรือ Vercel Cron) รายการวิ่งยังอยู่ แสดง "หลักฐานถูกลบตามนโยบาย" — ถ้ารายการยังรอตรวจตอนครบ 90 วัน ให้ลบตามกำหนดเช่นกัน (ไม่ควรเกิดเพราะมีกฎย้อนหลัง 7 วัน) |
| F4 | ⚠️ คำขอลบข้อมูล — ลบอะไรบ้าง? | ลบรูปทั้งหมดทันที, **ทำให้เป็นนิรนาม** (anonymize) บัญชี: ชื่อ → "ผู้ใช้ที่ลบแล้ว #xxxx", ลบรหัสพนักงาน/บัญชี auth, เอาออกจากตารางคะแนนทุกฤดูกาล — ส่วน audit log เก็บแค่ UUID ที่ไม่ผูกตัวตนแล้ว (ตามหลักเก็บเท่าที่จำเป็นเพื่อความโปร่งใสของกิจกรรม) ต้องให้ฝ่ายกฎหมาย/DPO ยืนยัน |
| F5 | ระยะเก็บ audit log | 2 ปี (ตั้งได้) |
| F6 | ภูมิภาคฐานข้อมูล | Supabase region Singapore (`ap-southeast-1`) — latency ต่ำ ต้องระบุในประกาศความเป็นส่วนตัวว่าเก็บข้อมูลนอกประเทศ |
| F7 | ประกาศความเป็นส่วนตัว / ความยินยอม | แสดงตอนล็อกอินครั้งแรก กดยอมรับ บันทึก `consented_at` + เวอร์ชันประกาศ (เนื้อหาประกาศให้องค์กรเป็นผู้จัดหา) |

## G. Real-time บน Vercel (คำแนะนำ)

Vercel Functions เป็น serverless ถือ WebSocket ค้างไว้ไม่ได้ จึงแนะนำ:

1. **Supabase Realtime — Broadcast จาก DB** (แนะนำ): trigger บนตาราง `leaderboard_entries` เรียก `realtime.broadcast_changes()` ไปที่ channel `season:{id}:leaderboard` ฝั่ง client subscribe ตรง ไม่ผ่าน Vercel
   - ส่งเฉพาะข้อมูลที่เปลี่ยน (user_id, points, rank, previous_rank) → ข้อมูลเล็ก รองรับผู้ชม 1000 คนพร้อมกันได้สบายใน plan Pro (โควต้า 500 concurrent ใน Free อาจไม่พอ → **ต้องใช้ Pro**)
   - ใช้ Realtime Authorization (RLS บน `realtime.messages`) ให้เฉพาะผู้ล็อกอิน
2. ค่า fallback: ถ้า socket หลุด → polling ทุก 30 วินาทีผ่าน endpoint ที่ cache ด้วย `revalidate`
3. ไม่ใช้ Postgres Changes ตรงๆ เพราะต้องตรวจ RLS ทีละผู้ชม ช้ากว่า Broadcast เมื่อมีผู้ชมมาก

อัปเดตอันดับเกิดเมื่อ "อนุมัติ" เท่านั้น (ไม่ใช่ตอนส่ง) ดังนั้นความถี่ต่ำ — แค่หลักร้อยครั้งต่อวัน

## H. ขอบเขตเทคนิค (สมมติฐาน)

- Next.js 15 App Router + TypeScript, Server Actions/Route Handlers, `@supabase/ssr`
- คำนวณคะแนน/อันดับ **ใน Postgres** (ฟังก์ชัน + trigger) เพื่อความถูกต้องเป็นแหล่งเดียว และมี mirror เป็น pure TypeScript สำหรับ unit test/preview ฝั่ง client — test ทั้งสองฝั่งด้วยชุดข้อมูลเดียวกัน
- ทดสอบด้วย Vitest (TS) และ pgTAP หรือ SQL test ผ่าน `supabase test db`
- i18n: `next-intl`
- แอนิเมชัน: CSS transform + FLIP (ไม่ใช้ library หนัก) ปิดเมื่อ `prefers-reduced-motion: reduce`
- Repo ปัจจุบันว่าง จะสร้างโครงสร้างใหม่ทั้งหมด
